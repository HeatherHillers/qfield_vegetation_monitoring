Why Dynamic Binding vs Singleton for Property Propagation

Question

Why do we use dynamic binding (Qt.binding()) to propagate plotId from parent to child components instead of setting it in a singleton object that would be accessed by the elements that need it?

Answer

The dynamic binding approach is superior to using a singleton for several important reasons:

1. Timing and Instantiation Issues

With a Loader, components are created dynamically. The timing problem with a singleton would be:

  • When onLoaded fires, you need the component to immediately have the correct plotId
  • If you relied on the singleton, the component would need to:
    1. Wait for the singleton to be initialized
    2. Add a Connections block to watch for changes
    3. Handle the case where plotId might not be set yet

With Qt.binding(function() { return plotId }), the component immediately establishes a reactive connection to the parent's property at the moment it's loaded.

2. Automatic Reactivity vs Manual Signal Handling

Dynamic bindings leverage QML's reactive system:

// Current approach - automatic
item.plotId = Qt.binding(function() { return plotId })
// Whenever parent.plotId changes, item.plotId automatically updates

With a singleton, you'd need explicit signal handling everywhere:

// Singleton approach - manual
Connections {
    target: AppState  // singleton
    function onPlotIdChanged() {
        myLocalPlotId = AppState.plotId
    }
}

This means more boilerplate code in every component that needs the data.

3. Lifecycle Management

This is critical with Loaders that create/destroy components:

✓ Bindings

Automatically cleaned up when the component is destroyed

Component.onDestruction: {
    // Nothing needed,
    // binding is auto-released
}

✗ Singleton

Need manual disconnect logic or risk memory leaks/stale connections

Component.onDestruction: {
    AppState.plotIdChanged
        .disconnect(myHandler)
}

4. Clear Data Flow

Bindings create an explicit parent→child data flow that's easy to trace:

Main QML sets plotId 
    → Loader.item.plotId (via binding)
        → Child components access via their parent

With a singleton, the data flow is hidden - any component anywhere can access/modify it, making debugging harder.

5. Multiple Instances / Plugin Isolation

Even though you only have one plugin now, if you ever needed multiple instances or wanted to test components in isolation, the dynamic binding approach keeps each instance independent. A singleton would cause all instances to share the same plotId, creating conflicts.

The Key Insight

Qt.binding() creates a managed, automatic, lifecycle-aware reactive connection. It's not just about passing a value once - it's about maintaining a live connection that:

  • Updates automatically when the source changes
  • Is established at exactly the right moment (onLoaded)
  • Cleans itself up when the component is destroyed
  • Follows QML's declarative programming model

A singleton would require you to manually recreate all this behavior using signals, connections, and explicit cleanup - which is exactly what Qt.binding() does for you automatically.

Example from Code

See demo4 and demo5 where this pattern is used:

Loader {
    id: dataControllerLoader
    source: "d5_strata_data_controller.qml"
    onLoaded: {
        // Establish reactive binding
        item.plotId = Qt.binding(function() { return plotId })
        item.currentStratum = Qt.binding(function() { return strataCode })
    }
}

The bindings ensure that whenever plotId or strataCode change in the parent, the loaded component's properties automatically update without any manual signal handling.
